Anonymous email authentication on Supabase

Users sign in with a code sent to their email. The application database never stores the address. This document specifies the schema, the Edge Functions, the RLS policies, and the operational rules that make that claim true rather than aspirational.

Audience: the engineer implementing auth. Companion artifact: LGBTQ UT App prototype, Account pane.

1. The problem

Supabase Auth writes the user's address to auth.users.email. For most products that is unremarkable. For a queer resource directory operating in Utah it is a liability: a subpoena, a breach, or a future administrator with different politics all resolve to the same exposure, and the people most at risk are the ones least able to absorb it.

The requirement is therefore stronger than encryption at rest. It is that the address is not present in the project at all, so the honest answer to a request for user emails is that there are none to produce.

Two mechanisms are needed together. A proxy alias makes mail deliverable without a stored destination. A blind index makes an account findable at login without a stored address. Neither is sufficient alone.

2. Architecture

The alias becomes the Supabase identity. auth.users.email holds chosen-twist-631@anonymous.appuser.io, not the real address. Delivery works because the forwarder resolves the alias; lookup works because of a peppered hash. The real address exists in exactly one system, and it is not this one.

WHO HOLDS WHAT
System Holds Real address?
Supabase Auth Alias as identity, user UUID No
Supabase Postgres HMAC hash, alias, username, DOB No
Supabase Vault HMAC pepper No
Forwarder (SES + Lambda) alias → destination map Yes — the only copy

Run the forwarder in a separate AWS account from anything else the project owns. The separation is the control; co-locating it with application infrastructure defeats the design.

Why not Cloudflare Email Routing

It is free and it forwards correctly, but every destination must confirm itself through a Cloudflare-sent verification email before routing begins. That inserts a second inbox round-trip into signup, and it fails silently for anyone who does not complete it. SES plus a Lambda is more setup and fully programmatic. Use Cloudflare only if signup friction is acceptable.

3. Schema

create table public.profiles (
  id           uuid primary key references auth.users(id) on delete cascade,
  email_hash   bytea not null unique,   -- HMAC-SHA256(normalized, pepper)
  alias        text  not null unique,   -- chosen-twist-631@anonymous.appuser.io
  username     citext not null unique,
  dob          date  not null,          -- age gate: 18+ / 21+
  created_at   timestamptz not null default now()
);

create unique index profiles_email_hash_idx on public.profiles (email_hash);

-- Public profile is a separate row so it can be deleted without
-- destroying the account.
create table public.public_profiles (
  id           uuid primary key references public.profiles(id) on delete cascade,
  display_name text not null,
  pronouns     text,
  county       text,
  bio          text,
  links        text[] default '{}',
  avatar_url   text,
  header_url   text
);

Store dob, not a computed age or a boolean. The 18+ and 21+ gates are evaluated against it at read time, so a user crosses each threshold on the correct day without a migration.

Never add an email column to profiles, not even nullable, not even "temporarily during migration." A nullable column is an invitation, and the first person to fill it will not be the last.

4. Row-level security

alter table public.profiles enable row level security;

-- No client policy exists for email_hash or alias. Deny by default:
-- with RLS on and no permissive policy, PostgREST returns nothing.
create policy "own row, safe columns"
  on public.profiles for select
  using (auth.uid() = id);

revoke all on public.profiles from anon, authenticated;
grant select (id, username, dob) on public.profiles to authenticated;

alter table public.public_profiles enable row level security;

create policy "public profiles are readable"
  on public.public_profiles for select using (true);

create policy "own public profile is writable"
  on public.public_profiles for all
  using (auth.uid() = id) with check (auth.uid() = id);

Column-level grants matter more than the policies here. A permissive select policy still exposes every column the role can reach, so email_hash and alias are withheld at the grant level and touched only by the service role inside Edge Functions.

5. Edge Functions

Two functions handle every path where a plaintext address exists. Both run on the service role, and in both the address lives only in local scope for the duration of the call.

POST /auth-start

// in:  { email: string }
// out: { status: "code_sent" }            ← identical for new and existing

const normalized = email.trim().toLowerCase();
const pepper     = await vault.get("EMAIL_PEPPER");
const hash       = hmacSha256(normalized, pepper);

let profile = await db.from("profiles")
  .select("id, alias").eq("email_hash", hash).maybeSingle();

if (!profile) {
  const alias = mintAlias();                  // adjective-noun-NNN@…
  await forwarder.register(alias, normalized); // leaves our infrastructure
  const { user } = await admin.createUser({ email: alias,
                                            email_confirm: true });
  await db.from("profiles").insert({ id: user.id, email_hash: hash,
                                     alias, username, dob });
  profile = { id: user.id, alias };
}

await admin.signInWithOtp({ email: profile.alias });  // routes via forwarder
return { status: "code_sent" };
// `normalized` goes out of scope here and is never persisted or logged.

Return the same response whether or not the account existed. A distinguishable response turns this endpoint into an oracle for whether a given person has an account in a queer directory, which is precisely the disclosure the design exists to prevent. Rate-limit by IP regardless.

POST /auth-verify

// in:  { email: string, code: string }
// out: { session }

const hash    = hmacSha256(email.trim().toLowerCase(),
                           await vault.get("EMAIL_PEPPER"));
const profile = await db.from("profiles")
  .select("alias").eq("email_hash", hash).single();

return await auth.verifyOtp({ email: profile.alias, token: code,
                              type: "email" });

6. Operational rules

The architecture above is correct and still leaks if any of the following is missed. Each has a default that works against you.

Rule Why the default fails
Pepper in Supabase Vault A pepper in an env var or the repo sits beside the hashes it protects. Email space is enumerable — an unpeppered hash is reversible in minutes.
Disable Edge Function request logging Supabase logs function payloads by default. The address arrives in the request body, so logging writes to disk exactly what the schema refuses to store.
Custom SMTP pointed at the forwarder Supabase's built-in mailer and default templates echo the recipient address into logs and headers you do not control.
Normalize before hashing Trim and lowercase, nothing more. Stripping Gmail dots and plus-tags also collapses people who use tagged addresses deliberately.
Set forwarder log retention to zero SES writes recipients to CloudWatch by default. The mapping is meant to be the only copy; logs quietly make a second.
Never log the request body on error The most common leak. An exception handler that dumps its input publishes the address to whatever aggregator is attached.

7. Consequences to accept

No unprompted email. There is no address to send to. Every alert, offer, and newsletter is a push notification. The prototype already assumes this; the Alerts pane is built around device tokens.

Newsletters by inbox require an opt-in. When a user enables it, the alias becomes a live forwarding target — mail reaches them, and the destination still stays with the forwarder. This is the single feature the pure-hash approach could not deliver, and the reason the alias earns its place.

Support cannot identify a user by email. Given an address, an admin can compute its hash and find the row — but only through a deliberate, audited tool. Build that tool consciously or people will improvise something worse.

Rotating the alias is the real block button. Mint a new one, drop the old forward, and every party holding the previous address is cut off at once, with nothing exposed in the process.

Open decision, deliberately unresolved: whether admins get the hash-lookup tool at launch. It is the difference between recoverable accounts and a clean conscience, and it should be a stated policy rather than an accident of implementation.
